# ProxyFlow V0.8 Product Scope

Status: Scope Freeze Draft

This document freezes the V0.8 product scope. New requests must pass the [Feature Admission Gate](product-direction.md#feature-admission-gate) before they can enter this release.

## One-Line Goal

> 让普通用户第一次能够从真实订阅开始，完成节点处理、策略选择、基础分流、兼容性检查，并导出可用的 Mihomo 或 sing-box 配置。

V0.8 is not measured by matcher count, configuration field count, or lines of code. It is complete only when the ordinary user workflow works end to end.

## User Acceptance Flow

```text
导入真实订阅
→ 刷新成功并建立 Last Known Good
→ 筛选美国、日本或香港节点
→ 创建 Manual / Auto / Failover Strategy
→ ChatGPT 走指定 Strategy
→ 国内流量走 DIRECT
→ 某类流量走 REJECT
→ 未匹配流量走默认 Strategy
→ 分别预览 Mihomo 和 sing-box
→ 对不兼容语义显示明确 blocker
→ 成功导出配置
→ Project export/import 后语义保持
```

Acceptance does not require the user to understand TrafficMatcherIR, Rule Set namespaces, Route Action, target schemas, or numeric priority.

## User-Visible Concepts

V0.8 Basic exposes:

- Source;
- Processing;
- Strategy;
- Routing Rule;
- Output.

Inspect is a capability across the workflow rather than another graph entity.

`routing-group`, `service-rule`, and `custom-rule` must not remain three parallel product entries. They are presented as one **Routing Rule** with these matcher choices:

```text
Service
Domain
CIDR
Port
Advanced
```

## Routing Rule Model

Service Rule and Custom Rule are not separate product features. They are matcher variants of the same Routing Rule.

Examples:

```text
Routing Rule
Matcher: Service
Service: ChatGPT
Target: US Auto
```

```text
Routing Rule
Matcher: Domain
Domain: example.com
Target: DIRECT
```

The implementation continues to use the existing typed matcher and TrafficMatcherIR model. The product must not expose a second rule system.

## Rule Group

Rule Group is a UI container only.

It may provide:

- a name;
- folding;
- ordering;
- batch enable or disable;
- visual grouping.

It must not own:

- a matcher;
- a target;
- a second priority;
- a second routing semantic.

A Rule Group must never compile into a hidden routing rule.

## Strategy Scope

V0.8 Basic Strategy includes:

- Manual;
- Auto;
- Failover.

A fixed node is configured as a Manual behavior and does not need to be a separate primary product type.

Load Balance keeps its existing internal model and validation, but it is Advanced and target-specific. It is not a shared Mihomo and sing-box Basic capability. A target that cannot preserve Load Balance semantics must report Unsupported and fail closed.

## Route Ordering

The visible rule order is the match order.

Basic UI uses list or drag ordering and does not expose numeric priority. Internally, deterministic priority remains:

- lower numeric value first;
- stable insertion order when priorities are equal.

Numeric priority is available only to Advanced or internal tooling.

## Routing Targets

V0.8 Basic supports:

- Strategy;
- DIRECT;
- REJECT.

Chain target is Advanced. Unsupported target semantics must fail closed.

Output does not act as a routing target. Final is presented as **Default Route** or **未匹配流量**, without requiring users to understand the Final IR entity.

## Advanced Scope

These capabilities remain available internally or through Advanced, but are not part of the V0.8 Basic workflow:

- ASN;
- GeoIP;
- GeoSite;
- Rule Set;
- target-specific matchers;
- Chain target;
- Load Balance;
- Universal IR Developer Preview;
- raw target diagnostics.

Every Advanced capability requires a clear target capability label and fail-closed behavior. It must not block the Basic workflow.

## Incremental Product Migration

> 保留已验证的底层 Project、IR、validation 和 compiler；在其上增加新的产品抽象层，逐步隐藏旧概念，而不是一次性重写全部 Routing UI 和数据模型。

Migration rules:

1. Continue reading legacy node types.
2. New projects expose only the unified Routing Rule.
3. Existing `service-rule`, `custom-rule`, and `routing-group` nodes use the unified Inspector.
4. Do not immediately delete old serialized fields.
5. Preserve Project round-trip compatibility.
6. Bump Project Schema only when a later implementation proves that compatibility cannot be maintained.

## Inspection Scope

The complete Route Inspector belongs to V0.9.

V0.8 retains lightweight inspection that:

- identifies the rule or Strategy blocking export;
- displays Mihomo and sing-box compatibility;
- locates a diagnostic on the canvas;
- reports a Strategy with no candidates;
- reports an invalid matcher or unsupported target.

V0.8 does not simulate a full route after the user enters a hostname, IP, or port.

## Out Of Scope

- complete Route Inspector;
- Runtime Service or backend implementation;
- server-side Scheduled Refresh;
- server-side Snapshot History;
- a third output target;
- support for every matcher;
- full client schemas;
- plugin system;
- arbitrary JavaScript;
- AI-generated configuration;
- node speed-test platform;
- accounts, multi-tenancy, or billing;
- broad protocol expansion;
- a large Routing UI rewrite;
- Project Schema bump unless later evidence proves compatibility impossible.

## V0.8 Release Gate

V0.8 can enter release preparation only when:

- the acceptance flow passes in browser QA;
- Basic exposes one Routing Rule model;
- target-specific capabilities are labeled accurately;
- unsupported semantics fail closed;
- Project export/import preserves routing semantics;
- Mihomo and sing-box representative binary validation passes;
- tests, build, and diff check pass;
- README and release notes describe only shipped capability.
