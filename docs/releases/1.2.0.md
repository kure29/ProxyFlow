# ProxyFlow 1.2.0

ProxyFlow 1.2.0 is a stable minor release with Mihomo, Surge, and Loon as the
supported production export targets. Mihomo remains the default target for new
Projects; sing-box remains registered with its compiler retained, but official
product export remains paused.

## Highlights

### Loon is now supported

Loon is now an ordinary supported product target through the complete product
path:

```text
New Project
  → Target Switch
  → Preview
  → compatibility diagnostics
  → .conf export
```

Loon Preview uses the real `loonState` compiler result. Workspace Export emits
the evidence-bounded artifact contract:

- `.conf` extension;
- INI format;
- `text/plain;charset=utf-8` MIME type.

### Loon real-client evidence

The accepted real client is Loon `3.5.0 (975)`. Real configuration import and
real proxy traffic passed. The real subscription projection contained `95`
candidates, with `91` compatible, `4` intentionally skipped, and `0` blockers.

OpenAI Service Rules have real-client acceptance covering recognition,
fetch/refresh, policy binding, traffic, and `FINAL -> DIRECT`. The other
first-party services have deterministic generation and semantic parity only;
they are not claimed as individually real-client proven. Routing precedence
acceptance covers only the documented controlled subset, including the proven
domain-family local-before-Remote case and the controlled Remote-vs-Remote
observation.

## Compatibility notes

Loon support is evidence-bounded and fail-closed. The supported product path
does not imply support for every native Loon feature. Unsupported or unproven
intent remains visible through compatibility diagnostics and blocks export
when it cannot be represented losslessly.

The following boundaries remain deferred or unsupported in this release:

- Proxy Chain;
- Reality;
- Vision / `flow`;
- SS2022 AES-256;
- SOCKS5;
- AnyTLS;
- TUIC;
- SSR;
- WireGuard;
- arbitrary remote rule-set formats;
- native Remote Proxy Source semantics;
- generalized different-policy Remote-vs-Remote ordering; and
- unsupported DNS combinations.

ProxyFlow's `ChainStrategyIR` represents actual multi-hop traffic order. The
accepted Loon evidence does not establish a lossless native proxy-chain
mapping, so `LOON_PROXY_CHAIN_UNPROVEN` remains intentional fail-closed
behavior. Proxy Chain is not implemented by this release preparation.

The ten first-party Service Rule assets retain their deterministic/semantic
parity boundary, and the shared mutable `proxyflow-rules` URL policy remains a
separate cross-target supply-chain design follow-up. No Loon-only URL pinning or
broader Service Rule client claim is introduced here.

## Upgrade

Self-hosted Stable installations continue to use the manager's stable channel:

```bash
/root/proxyflow.sh update
```

Managed Stable installations use `ghcr.io/kure29/proxyflow:latest`. Direct
Compose deployments can pin `ghcr.io/kure29/proxyflow:1.2.0` after the v1.2.0
container has been published.
